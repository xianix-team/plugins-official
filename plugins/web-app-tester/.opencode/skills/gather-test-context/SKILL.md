# Phase 1 — Gather Test Context

This skill is invoked by the **orchestrator** agent. It is not a standalone slash command.

## Inputs

| Variable | Source | Description |
|---|---|---|
| `MODE` | orchestrator | `test` (default) or `verify` (bug re-verification) |
| `ENTRY_TYPE` | orchestrator | `pr`, `issue`, or `wi` |
| `ENTRY_ID` | orchestrator | The PR number, issue number, or work item ID |
| `PLATFORM` | orchestrator | `GitHub` or `AzureDevOps` |
| `IS_PRODUCTION` | orchestrator | `true` when `ENVIRONMENT=production`; `false` otherwise (default) |
| `TEST_URL_SOURCE` + candidate URL | orchestrator (config resolution) | `arg-url`, `config`, or `scraped` — and the resolved URL when not `scraped` |
| `MUTATIONS_ALLOWED` | orchestrator (config resolution) | Set (authoritative) when the URL came from config; unset otherwise |
| `ROLE` / `STORAGE_STATE` / `AUTH_SETUP_COMMAND` | orchestrator (config resolution) | Auth context from `.web-app-tester.json`, if configured |

## Outputs

| Variable | Description |
|---|---|
| `MODE` | Passed through unchanged |
| `TEST_URL` | The URL the test plan will run against |
| `IS_PRODUCTION` | Passed through unchanged |
| `MUTATIONS_ALLOWED` | `true`/`false` — final read-only determination (see Step 3) |
| `TEST_PLAN` | Flat numbered list of test cases to execute, either found in the entry content or auto-generated from context (verify mode: the verification step plan) |
| `ENTRY_TITLE` | The PR title, issue title, or work item title — used in the report header |
| `PLAN_SOURCE` | How the test plan was obtained — one of: `auto-generated by web-app-tester`, `found in {PR | issue | work item} description` (naming the actual entry type), `sourced from acceptance criteria`, `sourced from bug repro steps` |
| `LINKED_PR_ID` | Azure DevOps only, `wi` entry: the PR linked to the work item (used for posting the report) |
| `STORAGE_STATE` / `ROLE` | Passed through unchanged for Phase 2 |
| `DECISIVE_CHECK` | Verify mode only: `BUG_SIGNAL` + `FIXED_SIGNAL` pair — see Verification Plan Derivation |
| `PRECONDITIONS` | Verify mode only: required data/state, each marked exists / must-create / unknown |

If a required output cannot be produced (e.g. no testable URL), this skill posts a comment and stops. Do not proceed to Phase 2.

For full provider command reference, see:
- `providers/github.md` (GitHub)
- `providers/azure-devops.md` (Azure DevOps)

## Step 1: Fetch Content

### GitHub — `ENTRY_TYPE == pr`

Resolve the `--repo` flag from the git remote before running gh commands:
```bash
REPO=$(git remote get-url origin | sed 's|.*github.com[:/]\(.*\)\.git|\1|;s|.*github.com[:/]\(.*\)|\1|')
```

```bash
gh pr view ${ENTRY_ID} --repo ${REPO} --json number,title,body,state,headRefName,baseRefName,url,author,labels,commits,closingIssuesReferences,comments
gh pr view ${ENTRY_ID} --repo ${REPO} --json closingIssuesReferences --jq '.closingIssuesReferences[].number'
```

For each linked issue number discovered:
```bash
gh issue view ${ISSUE_NUMBER} --repo ${REPO} --json number,title,body,state,labels,comments
```

Collect: PR title, description, all comments, commit messages, linked issue descriptions and comments.

---

### GitHub — `ENTRY_TYPE == issue`

Resolve the `--repo` flag from the git remote before running gh commands:
```bash
REPO=$(git remote get-url origin | sed 's|.*github.com[:/]\(.*\)\.git|\1|;s|.*github.com[:/]\(.*\)|\1|')
```

```bash
gh issue view ${ENTRY_ID} --repo ${REPO} --json number,title,body,state,labels,assignees,comments,projectItems
```

Discover linked PRs:
```bash
gh api "repos/${REPO}/issues/${ENTRY_ID}/timeline" --paginate \
  --jq '.[] | select(.event=="cross-referenced" or .event=="closed") | .source.issue.number // empty'
gh pr list --repo ${REPO} --search "${ENTRY_ID} in:body" --state all --json number,title,state,headRefName,url,body --limit 20
```

Collect: issue title, description, all comments, linked PR descriptions.

---

### Azure DevOps — `ENTRY_TYPE == pr`

Parse the remote URL and set `API_BASE`, `AZURE_REPO` per `providers/azure-devops.md`.

```bash
# PR metadata
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/git/repositories/${AZURE_REPO}/pullrequests/${ENTRY_ID}?api-version=7.1"

# PR threads (all comments)
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/git/repositories/${AZURE_REPO}/pullrequests/${ENTRY_ID}/threads?api-version=7.1"

# Linked work items
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/git/repositories/${AZURE_REPO}/pullrequests/${ENTRY_ID}/workitems?api-version=7.1"
```

For each linked work item, fetch to extract acceptance criteria or description:
```bash
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/wit/workitems/${WI_ID}?api-version=7.1&\$expand=all"
```

Collect: PR title, description, all thread comment contents (concatenated), linked work item descriptions and acceptance criteria.

---

### Azure DevOps — `ENTRY_TYPE == wi`

Parse the remote URL and set `API_BASE`, `AZURE_REPO` per `providers/azure-devops.md`.

```bash
# Work item with all fields and relations
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/wit/workitems/${ENTRY_ID}?api-version=7.1&\$expand=all"

# Work item comments
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/wit/workitems/${ENTRY_ID}/comments?api-version=7.1-preview.4"
```

**Auto-detect work item type** from `fields.System.WorkItemType`:
- `Bug` → extract repro steps (`Microsoft.VSTS.TCM.ReproSteps`) and root cause (`Microsoft.VSTS.Common.RootCause`). The repro steps are the **primary test plan seed** — treat them as a structured step list if they enumerate navigable steps.
- `Product Backlog Item`, `User Story`, `Feature` → extract acceptance criteria (`Microsoft.VSTS.Common.AcceptanceCriteria`).

**Verify mode:** the work item type must be `Bug`. Anything else → output one error line and stop: `Error: /verify-bug requires a Bug work item — #${ENTRY_ID} is a ${WORK_ITEM_TYPE}.` Also extract the Expected/Actual result fields when present (commonly embedded in `Microsoft.VSTS.TCM.ReproSteps` or `System.Description`).

**Discover linked PRs** from the work item relations (see `providers/azure-devops.md`). Store the first active (non-abandoned) linked PR ID as `LINKED_PR_ID`. If a linked PR is found, fetch its metadata and threads:

```bash
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/git/repositories/${AZURE_REPO}/pullrequests/${LINKED_PR_ID}?api-version=7.1"
curl -s -u ":${AZURE-DEVOPS-TOKEN}" \
  "${API_BASE}/_apis/git/repositories/${AZURE_REPO}/pullrequests/${LINKED_PR_ID}/threads?api-version=7.1"
```

Collect: work item title, description, repro steps or acceptance criteria, all work item comments, and (if a linked PR exists) linked PR description and all linked PR thread comments.

If no linked PR is found, set `LINKED_PR_ID=""` and continue — the testable URL will be scanned from the work item content directly, and the report will be posted on the work item itself.

## Step 2: Find the Test URL

**Config/arg resolution comes first.** If the orchestrator's config-resolution step produced a candidate URL (`TEST_URL_SOURCE` is `arg-url` or `config`), store it as `TEST_URL` and **skip the label-scan below entirely**. Comment-scraping is the fallback for repos without a config file or explicit URL argument.

The full precedence (resolved by the orchestrator, restated here): `--url` arg → `--env` arg → `defaultEnvironment` from `.web-app-tester.json` → comment-scraping (below) → stop with "no testable URL".

**Comment-scraping fallback:** scan all collected content (description, every comment, repro steps, commit messages) for a URL matching `https?://[^\s\)\"\']+`.

Prioritise URLs preceded by any of these labels (case-insensitive):
- `Preview URL:`
- `Staging URL:`
- `Test at:`
- `Deploy preview:`
- `Demo:`
- `Environment:`

Exclude URLs that appear inside fenced code blocks (``` or `~~~`).

**If no URL is found**, post the appropriate "no testable URL" comment via the correct provider and STOP — do not proceed to Phase 2:

- GitHub PR → `providers/github.md` "No URL Found — PR" command
- GitHub Issue → `providers/github.md` "No URL Found — Issue" command
- Azure DevOps PR → `providers/azure-devops.md` "No URL Found — PR" command
- Azure DevOps Work Item → `providers/azure-devops.md` "No URL Found — Work Item" command

Store the found URL as `TEST_URL`.

## Step 3: Read-Only Determination

Determine `MUTATIONS_ALLOWED` — whether data-modifying test cases may run:

1. **URL came from config** (`TEST_URL_SOURCE=config`): the environment's `mutationsAllowed` flag is **authoritative** (default `false` when omitted). The URL substring heuristic is skipped entirely.
2. **URL was scraped or given via `--url`**: the 1.0 behaviour applies — if `IS_PRODUCTION=true` and the URL has no `staging`, `preview`, `dev`, `test`, or `localhost` indicator, the run is read-only (`MUTATIONS_ALLOWED=false`); otherwise `MUTATIONS_ALLOWED=true`.

When `MUTATIONS_ALLOWED=false`, data-modifying test cases will be skipped in the execution phase with reason `Skipped — environment is read-only`. No action is required here; this is enforced per test case in `skills/run-playwright-session/SKILL.md`.

## Step V1: Verifiability Triage (verify mode only)

Runs before any browser work. Skip this step entirely when `MODE=test`.

From the bug's description, repro steps, and comments, classify the bug as **browser-verifiable** or not. A bug is *not* browser-verifiable when its observable failure lives outside a browser UI — e.g. backend-only (service crash, log error, data corruption with no UI surface), API-only (wrong response body/status observed via API client), or build/tooling (compile error, pipeline failure).

**If not browser-verifiable → stop. No browser is launched.**

- Interactive: tell the user why the bug cannot be verified in a browser; post nothing.
- Autonomous: post a brief comment on the bug via the correct provider — `🤖 web-app-tester could not verify — not browser-verifiable: <reason>` — then stop.

---

## Step V2: Verification Plan Derivation (verify mode only)

Replaces Step 4/4b for verify runs. Skip when `MODE=test`.

From `Microsoft.VSTS.TCM.ReproSteps` + `System.Description` + Expected/Actual result fields + work item comments (ADO), or the issue body and comments (GitHub), derive:

1. **`TEST_PLAN`** — a numbered step plan: the repro steps, normalized to navigable actions (each step a single action with a verb, concrete page paths / element labels where the bug states them). Set `PLAN_SOURCE="sourced from bug repro steps"`. Do not post a plan comment in verify mode — interactive runs surface the plan at Gate A instead.
2. **`DECISIVE_CHECK`** — the single observation that discriminates the two verdicts:
   - `BUG_SIGNAL`: what the bug reporter observed — the *actual* result stated in the bug.
   - `FIXED_SIGNAL`: the *expected* result — which must be **positively observed** to conclude not-reproducible. Absence of the bug signal is never enough.
3. **`PRECONDITIONS`** — required data/state for the repro path (a specific record, a signed-in role, a feature flag), each marked `exists` / `must-create` / `unknown`.
4. **Per-step `MUTATING` flags** — mark every step that creates, updates, deletes, or submits data.

**If the Expected Result cannot be established** from the bug content, the decisive check cannot be built:

- Interactive: ask the user to state the expected result (one question), then continue.
- Autonomous: the verdict is `INCONCLUSIVE` with reason `expected result not stated in bug` — skip Phase 2 and hand straight to `skills/post-verdict-report/SKILL.md`, which posts per its INCONCLUSIVE rules.

## Step 4: Find a Test Plan (test mode only)

### Azure DevOps `wi` entry — Bug repro steps

If the work item type is `Bug` and the repro steps field contains a numbered or bulleted list with at least two action verbs (Navigate, Go to, Click, Fill, Verify, Assert, Check, Submit, Open, etc.) → use repro steps directly as `TEST_PLAN`, set `PLAN_SOURCE="sourced from bug repro steps"`, and skip to Phase 2. Do not post a comment.

If repro steps exist but are not in a structured step format, use them as context for Step 4b auto-generation.

### All other entry types — Scan for existing test plan

Scan the full body and all comments for a structured test case list meeting ALL of these criteria:
- Numbered or bulleted list
- Contains at least two action verbs from: Navigate, Go to, Click, Tap, Fill, Enter, Type, Verify, Assert, Check, Confirm, Ensure, Submit, Expect, Open, Close, Scroll, Select, Upload
- Appears under a heading or label such as: `Test Plan`, `QA Steps`, `Testing Steps`, `Acceptance Criteria`, `Verification Steps`, or is an explicit numbered list of at least 3 test cases

Also accept a test plan generated by the `test-strategist` plugin (look for headings like `## Test Strategy`, `## Test Cases`, `## Automated Test Steps`).

**If a test plan is found:**
- Store it as `TEST_PLAN`.
- Set `PLAN_SOURCE`:
  - If found under `Acceptance Criteria` or in a work item's acceptance criteria field → `"sourced from acceptance criteria"`
  - Otherwise (PR/issue/work item body, comment, or test-strategist output) → `"found in {PR | issue | work item} description"`, naming the actual `ENTRY_TYPE` (e.g. `"found in issue description"` for an `issue` entry)
- Proceed directly to Phase 2.

**If no test plan is found** → run Step 4b.

---

## Step 4b: Auto-Generate Test Plan

Based on the title, description, commits, repro steps (Bug), acceptance criteria (PBI/Feature), and linked item content, derive a focused test plan as a flat numbered list of test cases. The test cases must cover each of the following:

1. **Primary user-facing change** — the core behaviour described or implied
2. **Implied UI interactions** — forms, navigation flows, state changes, error states
3. **Happy-path scenario** — the expected successful user journey
4. **Edge / negative scenario** — at least one boundary or error case

For **Bug work items**: the repro steps define the unhappy path — include them verbatim as test cases and add verification test cases that confirm the fix resolves them.

Format each test case as a single numbered action with a verb. Keep test cases concrete and navigable (reference page paths, button labels, form fields as described in the content).

Post this plan comment via the correct provider before executing:

- GitHub PR → `providers/github.md` "Auto-Generated Plan — PR" command
- GitHub Issue → `providers/github.md` "Auto-Generated Plan — Issue" command
- Azure DevOps PR → `providers/azure-devops.md` "Auto-Generated Plan — PR" command
- Azure DevOps Work Item → `providers/azure-devops.md` "Auto-Generated Plan — Work Item" command (posts on `LINKED_PR_ID`)

Store the auto-generated plan as `TEST_PLAN` and set `PLAN_SOURCE="auto-generated by web-app-tester"`.
